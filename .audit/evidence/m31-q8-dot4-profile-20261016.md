# Diagnostic ROCm kernel profile: Q8 dot4 prepack

## Finding

At a 2,048-token prompt on GPU2, the profiled Q8 dot4 attention kernel took
272.6 ms across 32 launches, compared with 111.3 ms for default Flash
Attention across 32 launches. The candidate kernel was about 2.45 times slower
for this short-context shape. The extra Q-prepack kernel added 8.3 ms across
32 launches. Q4_K matrix multiplication remained the largest stage, at about
5.28 s (65.4%) in the default trace.

This is profiler evidence used to locate cost, not a wall-time benchmark. One
profile was collected per path; profiler overhead and sampling variation make
the aggregate kernel-time totals unsuitable for reporting end-to-end latency.

The profiler's full summed kernel durations were 8.069 s default and 8.255 s
prepack. Do not interpret that 2.3% difference as a wall-time result. The
trace does show that prepack launch overhead is small at 2K; the selected dot4
attention kernel itself is the larger measured cost in this short-context
profile. At 64K the attention share may be different, so the target-context
comparison is still required before rejecting the candidate entirely.

## Next action

Do not tune the prepack launch based on this trace. First run a guarded 64K
default-versus-prepack comparison after both MI50 caps are verified at 180 W.
If dot4 remains slower at the target context, remove the candidate and retain
the existing Flash Attention path. If it wins only at long context, consider
dispatching it only above the measured break-even context length.

## Source-level follow-up

The profile's kernel symbols and the GFX906 launch configuration expose a
plausible reason the dot4 CTA loses at 2K. The candidate symbol
`flash_attn_tile<256,256,4,6,...>` processes 24 query/head cells per CTA; the
default symbol `flash_attn_tile<256,256,16,2,...>` processes 32. In the
GFX906 configuration table, those shapes request 384 threads and 256 threads,
respectively, both at target occupancy 2. So the candidate schedules 50% more
threads per CTA for 25% fewer query/head cells, while also packing Q and
transposing Q8 K into LDS. This is a source-supported hypothesis for the
slowdown, not a measured causal split.

The profiler already shows that Q prepack itself is only 8.3 ms across 32
launches, while the attention kernel is 161.2 ms slower than default. Future
work should focus on the dot4 CTA schedule and instruction path, not optimizing
the standalone prepack launch. A larger 48-cell GQA6 tile has since been added
as an opt-in candidate. It still needs operator correctness and matched
target-context timing; the original 24-cell candidate remains the only measured
dot4 tile, and full-model correctness is unverified.

## Larger GQA6 tile compile check

Added an opt-in 8-token by 6-head (48-cell) tile using the existing
`FLASH_ATTN_EXT` path. The first config requested 512 threads, which gave each
thread three half values in one shared-memory transfer; `ggml_cuda_memcpy_1`
only supports 1, 2, 4, 8, or 16-byte transfers, so HIP compilation correctly
rejected that instantiation. Reducing the CTA to 384 threads gives four half
values (8 bytes) per lane. The complete `ggml-hip` target then built for
`gfx906` with ROCm 6.2.41133 (AMD clang 18). The local linker expected
`libxml2.so.2`, while the host provides `.so.16`; a private symlink under
`/tmp/m31-libxml-compat` let the compiler run, with a linker warning about the
missing old symbol-version metadata. The commands were:

```sh
mkdir -p /tmp/m31-libxml-compat
ln -sf /usr/lib/x86_64-linux-gnu/libxml2.so.16 /tmp/m31-libxml-compat/libxml2.so.2
export LD_LIBRARY_PATH=/tmp/m31-libxml-compat:${LD_LIBRARY_PATH:-}
cmake -S . -B /tmp/m31-gqa48-build -DGGML_HIP=ON -DAMDGPU_TARGETS=gfx906 \
  -DCMAKE_BUILD_TYPE=Release -DLLAMA_BUILD_TESTS=OFF -DLLAMA_BUILD_EXAMPLES=OFF
cmake --build /tmp/m31-gqa48-build --target ggml-hip --parallel 4
```

The source at build time matches commit `47503dfc2`. This compile check is not
the pinned ROCm 7.2.1 build, and it does not establish runtime correctness or
performance.

The same branch was then built on Machinist from a clean detached worktree at
`176480a57a5b18be94efdc7f97b9130545775860`, using the pinned image ID
`50ff28a28cc13a3ca7333cd0c70e322d16245967c5fdf0d30a1bf57bda80a512`
(`localhost/miinfer-dev:rocm-7.2.1`). The full `ggml-hip` target completed for
`gfx906`; ROCm 7.2.1 emitted loop-unroll warnings but no errors. The container
could not follow the worktree's `.git` pointer to the host repository, so CMake

host before building. This was a compile-only check: no GPU tests or
benchmarks ran, and the live caps were still 225 W / 300 W.
